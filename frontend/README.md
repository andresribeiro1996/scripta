# Scripta (frontend)

The real app, branded "Scripta": React + Vite + TypeScript, Tailwind CSS, TanStack Query, React Router, installable as a PWA. Talks to all seven of the [backend](../backend/README.md)'s modules — `auth`, `library`, `gallery`, `covers`, `socials`, `arena`, and `murals` (its own "Modules at a glance" table is the skim layer for those). Replaces the old static, drag-your-own-file [viewer](../viewer/README.md) — accounts now, one library per signed-in user instead of a local file each time.

## Running it

The backend needs to be running first (`cd ../backend && npm run dev`), then:

```bash
cd frontend
npm install
npm run dev
```

Opens at `http://localhost:5173`. `VITE_API_URL` in `.env` points at the backend (defaults to `http://localhost:3000`, matching the backend's default `PORT`).

If you change the frontend's port or domain, update the backend's `FRONTEND_URL` in `backend/.env` to match — the backend's CORS policy only allows that one origin.

## What's here

- **`/login`** — signup collects email + username + password; login takes one field (either email or username) + password. Toggle between the two modes. Also a "Sign in with Google" link if the backend reports it's configured (`GET /auth/providers`).
- **`/oauth-success`** — where Google's login flow lands back; reads the tokens out of the URL fragment (see `backend/src/modules/auth/plugin.ts` for why they ride there instead of a request body) and decodes the access token's own claims locally rather than spending a `/auth/me` round trip.
- **`/choose-username`** — where a Google sign-in without a username yet gets routed on its first login (Google doesn't hand you one the way a signup form does). `RequireUsername` (nested inside `RequireAuth`, see `App.tsx`) is what redirects there — a password-signup account never sees this screen, since it picks a username at signup time.
- Everything past that point (`RequireAuth` *and* `RequireUsername`, so: `/login` if not signed in, `/choose-username` if signed in but without one) sits inside `src/layouts/DashboardLayout.tsx` — a persistent left sidebar (Library / Series / Collections / Gallery / Murals / Arena / Library style / Settings, plus account name and "Log out") wrapping a routed `<Outlet>`. The pages (see "Pages at a glance" above), each with its own section or bullet here:
  - **`/dashboard`** (`LibraryPage.tsx`) — loads the account's saved library via `GET /library`. Import accepts the same three formats the old viewer did — a `library.json` from the [exporter](../exporter/export.py), a `KoboReader.sqlite` straight off the device's USB drive, or a Goodreads library CSV export — auto-detected by content (magic bytes / header shape), never by filename. See `src/lib/fileImport.ts`, `sqlite.ts`, `goodreads.ts` — direct ports of the viewer's identical logic, kept in sync by hand since the viewer is being retired rather than shared as a common module. The first import for an account is saved as-is; every import after that is **merged** into what's already saved rather than replacing it (see below).
  - **`/dashboard/series`** and **`/dashboard/collections`** (`SeriesPage.tsx` / `CollectionsPage.tsx`, both thin wrappers around the shared `GroupsPage.tsx`) — see "Series and collections" below.
  - **`/dashboard/style`** (`LibraryStylePage.tsx`) — see "Library style" below.
  - **`/dashboard/settings`** (`SettingsPage.tsx`) — account email (read-only) and username, with a "Change" action that reuses the same `setUsername` call `/choose-username` uses. Also renders `SocialsSection.tsx` — see "Socials" below.
  - **`/dashboard/gallery`** (`GalleryPage.tsx`) — the account's image pool — see "Gallery and custom book covers" below.
  - **`/dashboard/murals`** and **`/dashboard/murals/:muralId`** (`MuralsListPage.tsx` / `MuralEditorPage.tsx`) — see "Murals" below.
  - **`/dashboard/arena`** and **`/dashboard/arena/:id/seed`** (`ArenaListPage.tsx` / `ArenaSeedPage.tsx`, plus the accountless public `/arena` pages) — book-bracket tournaments; the backend README's `arena` section covers the model and its routes.
- **Book cards** — a direct port of the viewer's poster-overlay design (`src/components/BookCard.tsx`), now resolving covers with exactly one backend call (`GET /covers/resolve` — the old client-side Kobo CDN → Open Library chain moved server-side behind a global cache; see "Auto cover resolution" below) plus a plain fallback panel. Ran into, and fixed, the exact same `loading="lazy"` bug the viewer hit — see the comment at the top of `BookCard.tsx`'s `<img>`. No progress bar or colored status pill — read status shows as a plain text label under the title/author (`statusLabel()` in `lib/covers.ts`: "Not read" / "Reading" / "Finished"), and the highlight count badge (top-right, only when a book has highlights) is the only other overlay left.
- **PWA**: a manifest + service worker (`vite-plugin-pwa`) make this installable to a phone's home screen — icon, splash screen, offline asset caching. The icon is the "Scripta" logo, provided as a source JPEG (`scriptaimg.jfif`, project root) and processed into `public/favicon-48.png` (browser tab), `icon-192.png` (manifest, and `apple-touch-icon`), and `icon-512.png` (manifest, `purpose: "any maskable"`) — center-cropped to square from the 992×1070 source, since it wasn't quite square to begin with. The PWA manifest only actually gets injected in a production build (`npm run build`), not `npm run dev` — that's `vite-plugin-pwa` default behavior, not a bug, confirmed by inspecting `dist/manifest.webmanifest` after a build.

### Merging multiple library sources

A single account can import from more than one source — a Kobo `library.json` today, a Goodreads CSV next month — and expects one combined library, not the second import wiping out the first. `src/lib/merge.ts` owns this, called from `LibraryPage.tsx` right before every `PUT /library` after the first:

- **Book identity across sources** (`bookKey`): Kobo's `ContentID` and Goodreads' synthetic id aren't comparable, so books are matched by normalized ISBN first, falling back to normalized title+author for books without one on either side.
- **Field merge for a matched book**: the newest import wins for everything — title, author, status, progress, etc. — except:
  - **Cover** (`_coverUrl`): kept from whichever side actually has one. This field is *never* set by an importer — it's only ever written after `BookCard.tsx`'s `<img>` actually finishes loading a real cover in the browser (see below), so "has `_coverUrl`" means "a cover was genuinely confirmed," not just "had an ISBN to try."
  - **Highlights**: unioned (de-duplicated by `BookmarkID`), not replaced — re-importing the same source doesn't duplicate them, but a Goodreads review and a Kobo highlight on the same book both survive.
- **Unmatched books** from either side are kept as-is; existing ones keep their position, new ones are appended.
- **Top-level fields no importer ever sets** — the library's `name` (see below) and its `groups`, chief among them — survive a re-import: `mergeLibraryData` bases the result on `{...existing, ...incoming, ...}`, so `incoming` still wins for anything it actually specifies (source, schema_version, ...), but doesn't blank out fields it simply never had an opinion on. An earlier version of this spread `incoming` alone and silently dropped both on the *second* import — caught and fixed while building the library-naming feature; see test 7 in `scripts/test-merge.mts`.

Cover confirmation is persisted back to the account so future merges can rely on it: `LibraryPage.tsx` passes `onCoverResolved` into every `BookCard`, batches confirmations in a `Map` keyed by `bookKey`, and flushes a single debounced (1.5s) `PUT /library` reading the freshest React Query cache — not one save per card, and not a stale closure if the debounce fires late.

Verified with a standalone pure-logic test script (`scripts/test-merge.mts`, run via `npx tsx scripts/test-merge.mts`) and end-to-end in a real browser against the real backend (two-source import producing one merged book with the newer title/status, the original cover kept, and both sources' highlights present).

### Naming your library

`LibraryPage.tsx`'s header doubles as an inline-editable field — click the name (defaults to "Library" if you haven't set one) to edit, same interaction as renaming a series or collection. Saved as `name` on the library document (`api/library.ts`'s `LibraryData`), settable even before your first import (it saves `{books: [], name}`, a valid empty library). Never touched by an importer, so — thanks to the merge fix above — it survives every subsequent import untouched.

### Deleting books — select mode

An early version gave every `BookCard` its own "Delete" button. Deleting more than one or two books meant repeating a full click-confirm cycle per book, so this was replaced with a **select mode**: a "Select…" button in the page header (Library, Series, Collections all have their own) toggles the whole grid into a mode where clicking a card selects it (a checkmark badge, always visible, appears top-left) instead of doing anything else — dragging, the hover style-swap, and the "Style" button are all suppressed while it's on, since none of them make sense mid-selection. "Delete selected" then confirms once via `window.confirm` (`"Delete {N} book(s) from your library? This can't be undone."`) and removes every selected book in a single save, after which selection mode turns itself back off. Selecting just one book and deleting it still works fine — this isn't a "bulk-only" path, just a strictly better one.

Removes the selected books from `books` **and** scrubs their `bookKey()`s out of every group's `bookKeys` (`removeBooksFromAllGroups()`, `lib/groups.ts` — takes an `Iterable<string>` so a multi-book delete scrubs every affected group in one pass, not one call per book) in the same save — not strictly required for correctness (`booksInGroup()` already silently drops a dangling key), but leaving it in would mean a *different* book that happened to produce the same key later (a title+author collision, for books with no ISBN) could quietly inherit stale group membership, and it's just clutter in the saved data otherwise. `LibraryPage.tsx` and `GroupsPage.tsx` each own their own `selectionMode`/`selectedKeys` state and `handleDeleteSelected`, same "filter `books`, scrub `groups`, save" shape, following each page's own existing read/write pattern (direct `queryClient`/`saveLibrary` calls vs. the `useLibrary()` hook's `updateLibrary`).

**A real bug caught while building this**: the dark gradient scrim behind a card's title/author overlay (`BookCard.tsx`, rendered whenever `showTitleAuthor` is on — the default — or whenever a book has no cover at all) painted *after* the "Style"/"Delete" buttons in DOM order, and without `pointer-events: none` it silently absorbed every click over the whole card — including the visually-transparent area at the top where those buttons sit. For any book with no cover this made Style (and the old per-card Delete) permanently unclickable, not just under the default style. Fixed by adding `pointerEvents: "none"` to the scrim.

Verified with an updated pure-logic test script (`scripts/test-groups.mts`, `removeBooksFromAllGroups()` — including a genuine multi-key-in-one-call batch case, not just looped single-key calls) and end-to-end in a real browser: confirmed Style now opens for a cover-less book; confirmed selecting books across the Library grid (a series member and a standalone book together) and deleting them removed both and scrubbed the series member out of its series' `bookKeys`; confirmed selecting and deleting straight from a Series section correctly scrubbed the book from both that series and an unrelated collection it was also in; confirmed Cancel mid-selection leaves every book untouched (temporarily forced `window.confirm` to return `true` only for the actual delete calls, never relied on for Cancel since Cancel doesn't call it at all).

### Series and collections

`src/lib/groups.ts` defines a single `Group` shape — `{id, type: "series" | "collection", name, bookKeys, createdAt, updatedAt}` — that backs both the Series and Collections pages via one shared component, `src/pages/GroupsPage.tsx`. `bookKeys` references books by `bookKey()` (the same cross-source identity `lib/merge.ts` uses), not `ContentID`, so a group keeps meaning the same thing across a later re-import. `groups` lives as one more field on the library document — no backend change needed, same passthrough reasoning as everything else in this section.

The two differ only in one respect: **series are additionally auto-seeded** from each book's own `Series` field (`deriveSeriesGroups`, called from `LibraryPage.tsx` right after every merge) — a series-type group is created the first time a `Series` value is seen, and matching books keep getting added to it on later imports. This is strictly additive: it never renames, deletes, or removes a book from a series, so a manual rename or an intentional "this doesn't belong" removal survives future imports. Once seeded (or created by hand — both pages have an "Add series" / "Add collection" form for that), a series is an ordinary editable resource exactly like a collection: rename inline, delete, or open "Manage books" for a searchable checkbox picker over the whole library. A series' display order falls out of each book's own `SeriesNumber`; a collection has no inherent order and shows books in the order they were added.

Verified end-to-end in a real browser: importing books with a shared `Series` value auto-created one series group containing both, correctly ordered by `SeriesNumber`; creating a collection, adding a book via the picker, renaming it, and reloading all round-tripped through `GET`/`PUT /library` correctly.

### Library grid order — clustered by series, then by manual (drag-to-reorder) order

`src/lib/libraryOrder.ts` decides the *display* order of the main Library grid (`LibraryPage.tsx` only — the Series/Collections pages already have their own per-group ordering and are unaffected). Rules:

- **Series cluster together, ahead of any standalone book.** Every series with at least one resolvable member forms a block of its own books kept adjacent, `SeriesNumber`-ordered; clusters are placed before every non-series book, ordered among themselves by their earliest member's `_order` (see below). A book seeded into more than one series (possible by hand via `GroupsPage.tsx`'s "Manage books" picker) is placed once, in whichever cluster sorts earliest.
- **Collections deliberately do NOT participate.** They're an organizational tool (see the section above), not a layout one — a book being in a collection has zero effect on where it renders in the Library grid. Only series cause clustering.
- **Every other book keeps a manually-tracked `_order`.** `assignBookOrder()` (called from `LibraryPage.tsx`'s `handleFileChosen`, right after every merge/first-import) gives any book that doesn't already have one the next number after the current max, in that import's order — an importer never sets this field itself. Standalone books are sorted by it, and it's also what dragging a card changes (next).

**Drag-to-reorder**: every `BookCard` in the Library grid is reorderable (`reorderable` prop, wired up only by `LibraryPage.tsx` — Series/Collections detail views and the style-page preview don't pass it, so cards aren't reorderable there), driven by `@dnd-kit` — pointer press-and-hold (150ms activation delay, so touch dragging works and a plain tap still opens the book) plus Space/arrows keyboard dragging. Dropping card A onto card B moves A's whole top-level unit to sit immediately ahead of B's:
- If A is a standalone book, only A moves.
- **If A belongs to a series, the entire series moves as one block** — dragging any single card from a series drags the whole thing, never splitting it. This holds regardless of which specific card in the series you drag, or which specific card in the target series you drop onto.
- Since series always render ahead of standalone books no matter what (the rule above), dragging a standalone book "onto" a series card can't put it ahead of that series — it lands as the first standalone book, immediately after it, which is what actually happens (see `reorderOnDrop()`'s own comment for why the *display* result and the reasoning behind the underlying `_order` change can look different from what you'd expect at first).
- Dropping onto a card that's already part of the same unit being dragged (e.g. one series book onto another book in that same series) is a no-op.
- `reorderOnDrop()` fully renumbers every book's `_order` from the resulting sequence (`0..n-1`) rather than trying to preserve old magnitudes or insert fractional values — simple and always correct, at the cost of every book's `_order` value changing on every drag (harmless, since nothing besides display order depends on the specific number, only its relative position).

**The drop takes effect immediately, not after the network round trip.** `LibraryPage.tsx`'s `handleReorder` applies the new order to the React Query cache *before* calling `saveLibrary` — the dropped card visibly takes its new slot and whatever was there shifts out of the way right away; the `PUT /library` happens in the background, and a failure rolls the optimistic update back rather than leaving the UI showing an order that didn't actually persist. Where the browser supports the View Transitions API, the update is wrapped in `document.startViewTransition()` (via a small `updateWithViewTransition()` helper, using `flushSync` so React actually commits the DOM change inside the transition's callback) so the shift visibly animates — each card carries a stable `viewTransitionName` (`BookCard.tsx`, sanitized from its `bookKey()`, only set when reorderable) so the browser recognizes "this is the same card" across the reorder. Falls back to a plain, instant, unanimated update on any browser without support — never required, purely a nice-to-have. One real bug caught while building this: `startViewTransition()`'s `ready` promise (not `finished`) is what rejects with `InvalidStateError` when a transition gets skipped (a hidden document, or another transition already in flight — both routine, not real failures) — catching only `finished` left `ready`'s rejection unhandled, surfacing as a console error on every skipped transition. Both are now caught. Verified by installing an `unhandledrejection` listener and firing three rapid successive drags (the scenario most likely to overlap transitions) — zero rejections.

This is purely a render-time derivation — neither `orderLibraryBooks()` nor `reorderOnDrop()` touches the stored `books` array's own iteration order, which stays in plain merge order (see `lib/merge.ts`); `reorderOnDrop()` only rewrites each book's `_order` field. Getting `_order` to actually survive a merge needed the same fix `mergeLibraryData` already got for library-level fields, one level down: `mergeBookPair` was spreading only `incomingBook` as its base, silently dropping any app-managed field (like `_order`, or `_coverUrl` before it got special-cased) that only lived on the existing side. Fixed the same way — `{...existingBook, ...incomingBook, ...}` — while an importer's own fields still win per "newest wins."

Verified with two pure-logic test scripts (`npx tsx scripts/test-library-order.mts` — 16 checks covering clustering, collections' non-participation, and every drag-to-reorder case above; `npx tsx scripts/test-merge.mts` — gained a regression test for the `_order`-survives-a-merge fix) and end-to-end in a real browser: imported standalone and series books interleaved, confirmed the series cluster rendered first ahead of standalone books; re-imported to confirm a matched series book kept its `_order` while its other fields still updated, and a genuinely new book was appended correctly; simulated real HTML5 drag/drop events (`dragstart`/`dragover`/`drop` with a `DataTransfer`) to drag a standalone book onto another (confirmed only it moved) and to drag one series book onto a standalone book (confirmed the *whole* series moved, still `SeriesNumber`-ordered) — both confirmed persisted via a direct `GET /library` after each.

### Library style

`/dashboard/style` (`LibraryStylePage.tsx`) is meant to cover essentially everything about how a card and the page around it look, not just a curated few — Library, Series, and Collections all read the same settings, via two shared components: `BookGrid` (`src/components/BookGrid.tsx`, the grid's own layout) and `PageContainer` (`src/components/PageContainer.tsx`, the page area around it — width and padding — used by these three book-grid pages only, not Settings/Library style themselves). All 24 settings live in `style` on the library document (`lib/libraryStyle.ts`'s `LibraryStyleSettings`, resolved against defaults with `resolveLibraryStyle()` wherever it's read) — same reasoning as the library `name`: a deliberate per-account preference that should follow the account across devices, and (thanks to the merge fix above) survives a later import untouched since no importer ever sets it. `BookCard` takes the whole resolved `style` object as one prop rather than a growing list of individual ones — cleaner as this list keeps growing. The card-appearance sections (`CardAppearanceSection`/`CardBorderSection`/`CardContentSection`/`CardTextSection`, `src/components/StyleControls.tsx`) are shared with the per-series style panel below — see that section for why.

**Card layout** — card size (the `minmax()` floor in `grid-template-columns: repeat(auto-fill, minmax(cardMinWidth, 1fr))`; `auto-fill` gets responsive columns "for free" from one number instead of separate sm/md/lg breakpoint tiers), and spacing between cards / between rows (the grid's `column-gap` and `row-gap`, independent rather than one `gap` shorthand — compact horizontally with generous room between rows, or vice versa, is a reasonable thing to want and a shorthand can't express it). Library-wide only — see "Per-series style overrides" below for why this can't vary per series.

**Card appearance** — corner radius; cover shape (`cardAspectRatio`, one of `"2/3"`/`"3/4"`/`"1/1"`, applied straight to CSS `aspect-ratio` — no manual fraction math needed); a drop-shadow toggle; a hover-animation toggle (the lift/scale/deepen-shadow effect on `:hover`); card opacity (0–100%, the whole card — cover, text, everything — distinct from the border's own opacity below, applied as plain CSS `opacity`); and text-overlay darkness (0–100%, the strength of the dark gradient scrim behind the title/author text — scales both the gradient's near-stop and mid-stop opacities together, preserving the original shape of the gradient, just stronger or weaker).

**Card border** — five settings, not just width + color: width (px, `0` = no border); **which sides** (`cardBorderSides`, four independent booleans — top/right/bottom/left all share the one width/style/color/opacity, only their presence varies, since per-side widths would be a lot of extra sliders for a case nobody actually asked for); style (`cardBorderStyle` — solid/dashed/dotted/double/groove/ridge, straight off CSS `border-style`); color (optional, `null` meaning "use the theme's `--color-border`", same on/off pattern as the page background below); and opacity (0–100%, independent of the color itself so a chosen color can be faded without re-picking it). Opacity is the one genuinely non-trivial bit: `resolveBorderColor()` (`lib/libraryStyle.ts`) converts an explicit hex color to `rgba()` (an `<input type="color">` itself can't carry alpha), or wraps the theme-default CSS variable in `color-mix(in srgb, var(--color-border) N%, transparent)` when no explicit color is set — plain string return at 100% either way, no math. Directly unit-tested (`scripts/test-library-style.mts`) since it's the one place in this whole feature with real string logic to get wrong.

**Card content** — show title and author on cards. Off hides the title/author overlay (and its scrim, so a real cover shows unobscured) on any card that actually has a resolved cover. A book with no cover ignores this setting and always shows title/author regardless — there'd be nothing on the card at all otherwise. `BookCard.tsx`'s `CoverImage` reports whether it currently has something to show via `onHasCoverChange`, which `BookCard` combines with this setting into one `showOverlayText` flag gating both the scrim and the text block.

**Card text** — the title/author/status overlay's own typeface (`cardFontFamily`), base text size (`cardFontSize`), text color (`cardTextColor`, `null` meaning **white** — unlike almost every other "off" state in this file, which means "the app's theme default" — because this text always sits on a dark scrim over cover art, not the page background, so the app's light/dark theme is irrelevant to it), and two independent booleans, `cardBold`/`cardItalic`. Same em-based-children technique murals' block text uses (see that section below): `BookCard`'s root gets `fontFamily`/`fontSize` as an inline style, and the title/author/status elements are sized in `em` (`1.15em`/`0.9em`/`0.8em`) so they actually respond to it — Tailwind's rem-based `text-sm`-style utilities, which is what they used before this setting existed, measure against the document root and wouldn't move at all otherwise. Author and status keep the exact same relative *opacity* (0.82 / 0.6) the old hardcoded `text-white/82`/`text-white/60` classes had, now applied as real CSS `opacity` on top of whichever color is actually chosen, so the original visual hierarchy (title most prominent, status least) survives a custom color instead of only the title responding to it.

`cardBold`/`cardItalic` are applied per-element (title/author/status), not once on `BookCard`'s root, and each is set as `fontWeight: cardBold ? 700 : undefined`/`fontStyle: cardItalic ? "italic" : undefined` — deliberately `undefined`, never `"normal"`, when off. The status label carries its own `font-medium` Tailwind class for its baseline look; an inline style that's merely set to `"normal"` would still win over that class regardless of the toggle's state (inline styles always beat classes), silently flattening the label's weight even with `cardBold` off. `undefined` is the one value that truly doesn't touch `font-weight` at all, letting the class's own weight show through untouched — confirmed via `getComputedStyle` with the toggle off (status resolves to the class's `500`, title with no class of its own resolves to plain `400`) and on (both resolve to `700`).

**Six font choices, not three** — `cardFontFamily`'s three original entries (`sans`/`serif`/`mono`) are bare system-font-stack presets, no webfont loading; three more (`playfairDisplay`/`inter`/`jetbrainsMono`) are real, distinct typefaces, self-hosted rather than linked live from `fonts.googleapis.com` — same offline-friendly, serve-everything-from-this-app's-own-origin posture as the rest of the app. Each is one `.woff2` file under `frontend/public/fonts/`, declared via `@font-face` in `src/index.css`, Latin-subset-only (`unicode-range` matching what Google's own CSS API serves as the "latin" block — this app has no i18n need for Cyrillic/Greek/Vietnamese glyph data) and **regular weight only** — bold/italic are left to the browser's synthesized-style fallback (`font-synthesis`, on by default) rather than three more downloaded files per family; three real typefaces beats twelve files for marginally crisper synthesized styles on a personal app. `CARD_FONT_FAMILY_OPTIONS`/`BLOCK_FONT_FAMILY_OPTIONS` (`lib/libraryStyle.ts`) are two separately-declared arrays with the same six values, not a shared one — consistent with the isolation rule below. Confirmed live via `document.fonts` (not just that the CSS declares it) that a selected self-hosted font actually loads and its `status` flips to `"loaded"`.

**Page** — background color (an optional override applied to `DashboardLayout.tsx`'s `<main>`, the content area only — the sidebar keeps its own `--color-surface`; same "off by default, prefills with the live theme color via `getComputedStyle` when turned on" pattern as the border color), content width, and horizontal/vertical page padding (independent, same reasoning as the row/column gap split) — together, `PageContainer` replaces what used to be a hardcoded `mx-auto max-w-6xl px-5 py-8` on each of the three book-grid pages. Library-wide only, same reason as Card layout — see below.

The style page itself edits a local draft for instant UI feedback; most controls debounce the actual `PUT /library` (400ms, same pattern as the cover-confirmation flush in `LibraryPage.tsx`) so dragging a slider doesn't spam saves, while discrete controls (checkboxes, the `<select>`s) save immediately.

**The preview actually shows every setting, including the page-level ones.** It didn't at first — `BookGrid` alone only knows about card layout, so background color, content width, and padding changed nothing visible on this page even though they worked correctly everywhere else, with no way to confirm them without leaving to check Library/Series/Collections. Fixed by wrapping the preview grid in the same kind of frame those pages actually use: an outer `<div>` painted with the draft's background color (or the theme default), containing an inner `<div>` sized and padded exactly like `PageContainer` would. Content width is honest but capped — it can't grow past what this settings panel itself has room for, so a caption says as much rather than silently under-representing a large value. A second caption points out that shadow/hover only show up **on hover**, since a static preview can't demonstrate those on its own. The book data underneath is the account's own first few books if it has any, or four placeholders if not — two carrying a `_coverUrl` (an inlined SVG data: URI, so previewing needs no real network request) so the title/author toggle has something to actually demonstrate, and two without one to show the "always shown with no cover" rule at the same time.

**A real bug caught while building this**: the default `overlayIntensity` (88) and `contentMaxWidth` (1152) didn't sit exactly on their sliders' step grids (step 5 and step 20 respectively) — `<input type="range">` silently snaps a value that's off-grid to the nearest valid step the moment it renders, so the *actual* value shown (and eventually saved) on a fresh account diverged from the documented default (90 and a rounded-off width) before the user ever touched anything. Fixed by choosing steps that evenly divide each default (2 and 16). Guarded against regressing with a dedicated test script, `scripts/test-library-style.mts`, which checks every numeric default against its range for exactly this — including all the settings added afterward.

### Per-series and per-book style overrides — a three-level priority chain

Two more style panels, both opened from a "Style" button and both built on the same generic `PerCardStylePanel.tsx` (Card appearance/border/content controls shared via `StyleControls.tsx`, same as `/dashboard/style`):

- **A series** — its "Style" button (`GroupsPage.tsx`, series only; collections don't get one) overrides how every book in that series looks, taking priority over the library-wide style.
- **A single book** — every `BookCard` has its own small "Style" button (top-left, visible on hover; accent-colored once customized) opening a panel scoped to just that one book. Its override takes priority over **both** the series and the library-wide style — "priority over all others," literally: **library → series → book**, each level optional, each one winning outright over everything before it once it's set.

**Scope is deliberately narrower than the library-wide panel, at both levels**: only Card appearance/border/content/text — never Card layout (card size/spacing) or Page (background/width/padding). `lib/libraryStyle.ts` defines exactly which fields are eligible as `PER_CARD_STYLE_KEYS`, with `PerCardStyle = Pick<LibraryStyleSettings, ...>` as the type `Group.style` and a book's own `_style` both use. The reason is structural, not arbitrary: every card in the Library grid shares one CSS grid, so column sizing/gaps can't meaningfully vary per card without splitting the grid itself into separate sub-grids — a real option, just not one this needed, since appearance properties (border, shadow, opacity, font, ...) have no such constraint: each `BookCard` is styled independently via inline style regardless of the shared grid it sits in, so those *can* vary per card (or per series) with zero layout cost. `cardFontFamily`/`cardFontSize`/`cardTextColor` are ordinary `PER_CARD_STYLE_KEYS` entries like any other — since they're just three more fields in the same `Pick`, adding them to the library/series/book chain needed no changes anywhere else in the priority-resolution logic at all, only the new fields themselves plus `CardTextSection`'s UI.

**Isolated from mural blocks' own style, on purpose.** Mural blocks (see that section below) have their own independent font/size/color trio too, and it would have been easy to let `BlockStyle` reuse `PerCardStyle` — they used to share a type relationship (`BlockStyle` was `Omit<PerCardStyle, ...> & {...}`), which is precisely what broke the moment `PerCardStyle` grew these three text fields: `BlockStyle` silently inherited `cardFontFamily`/`cardFontSize`/`cardTextColor` right alongside its own `fontFamily`/`fontSize`/`textColor`, since the `Omit` never excluded them. Fixed by making `BlockStyle` a fully independent type declaration — no `Omit`, no intersection, no reference to `PerCardStyle` at all, just border fields that happen to share the same names (so `CardBorderSection` still works for both, via ordinary structural typing, not derivation). A book/series/library font choice and a mural block's font choice are two genuinely separate settings now, guaranteed by the type system rather than by convention — `scripts/test-library-style.mts` has a dedicated regression test for exactly this (checking `DEFAULT_BLOCK_STYLE` and `DEFAULT_LIBRARY_STYLE` each only ever carry their OWN field names, never the other's).

**Priority resolution**: `effectiveCardStyle(libraryStyle, seriesOverride, bookOverride)` (`lib/libraryStyle.ts`) applies each override, in order, over the library style — `undefined` at either level just skips it. Since both overrides are always a *complete* `PerCardStyle` object once set (see below), a book override doesn't blend field-by-field with the series' underneath it — it fully supersedes it for every per-card field at once; the series override only matters at all when there's no book override. On the Library grid, which series (if any) a book belongs to for style purposes has to agree with which series it's *displayed* under — `seriesGroupByBookKey()` (`lib/libraryOrder.ts`) is built from the exact same cluster-priority logic `orderLibraryBooks()` itself uses, so the two can never disagree. This lookup is keyed off the **full**, unfiltered group list (not whichever type the current page happens to show) — a book's true effective style doesn't change depending on whether you're looking at it from the Library grid, its series' own block, or a collection it's also in; `GroupsPage.tsx` resolves it the same way regardless of `type`.

**Customization is all-or-nothing, not per-field, at both levels**: `Group.style` and a book's `_style` are each either `undefined` (pure inheritance) or a complete `PerCardStyle` object — turning "Custom style" on seeds the panel's draft from *what that target currently looks like* (the effective style one level up the chain — a book seeds from its series' style if it has one, not a blank slate), so enabling customization is never a jarring visual reset, and every subsequent edit replaces the whole saved object, not just the one field touched. Turning customization off clears the override entirely (`setGroupStyle`/a book's `_style` set to `undefined`).

**A real bug caught while building the series panel** (and a defensive fix that outlived it, now protecting the book-level panel too): the original `SeriesStylePanel` passed its own full-object setters directly as the shared sections' patch-callback props — those sections call back with only a *partial* patch (e.g. `{cardOpacity: 30}`), same as `LibraryStylePage.tsx` correctly wraps with a merging function. Un-wrapped, every single-field edit collapsed the saved override down to just that one field, discarding the other 11. Now generalized into `PerCardStylePanel.tsx` with the correct `applyPatch`/`savePatchNow` wrapping built in once, used by both levels. The read side got hardened at the same time, on its own merits — a `Group.style` this incomplete crashed `CardBorderSection` outright (`draft.cardBorderSides.top` on a `cardBorderSides` that was simply missing). Fixed with `resolvePerCardStyle()` (same pattern as `resolveLibraryStyle()`, one level down), used by both panels' initial draft and `effectiveCardStyle()` itself — so an incomplete override, at either level, for *any* reason, can never crash rendering again.

**A methodology bug caught while building the book-level panel, unrelated to the feature itself**: every `tsc --noEmit -p .` check run throughout this whole session had been silently checking *nothing* — the root `tsconfig.json` is a solution-style file (`"files": []`, only project references), and `-p .` without `-b`/`--build` mode just resolves zero files to check, exiting 0 regardless of real errors. Caught when a genuine `Cannot find module` error (a leftover `SeriesStylePanel` import after the rename above) still reported a clean exit. The project already had a correct `npm run typecheck` script (`tsc -b --noEmit`) that was never being used. Every check from this point on uses that script (or `tsc --noEmit -p tsconfig.app.json` directly) instead — confirmed against the whole project afterward (a full `npm run build` too) to make sure nothing from earlier in the session had slipped through undetected; nothing had.

Verified with new pure-logic test coverage (`scripts/test-library-style.mts` gained a dedicated three-level chain test — book fully superseding series, series alone still beating library, book-with-no-series still beating library, layout untouched throughout — on top of its existing `extractPerCardStyle`/`effectiveCardStyle`/`resolvePerCardStyle` coverage; `scripts/test-library-order.mts`'s existing `seriesGroupByBookKey` coverage) and end-to-end in a real browser: customized a series' radius, confirmed both its books picked it up; opened a book's own panel and confirmed it seeded from the *series-resolved* value (not the library default); set a distinct book-level radius and confirmed, on the same grid, all three books rendering with three independently-correct radii simultaneously (book override, series override, library default); added that book to a collection and confirmed its book-level override still won there too — the exact cross-page scenario the `seriesGroupByBookKey`-over-the-full-list fix exists for; confirmed persistence via a direct `GET /library`; and confirmed zero JS errors via an injected `window.onerror` listener (the browser tool's own console log doesn't reset across navigations, so a fresh listener was necessary to tell a stale cached error apart from a real new one).

**Card text specifically** was verified the same way, plus with `getComputedStyle` (not just visual inspection): set the library-wide font to Monospace/18px/a custom yellow through the real panel, then confirmed a preview card's wrapper resolved to exactly the monospace stack at `18px` in that yellow, its title computed to exactly `18 × 1.15 = 20.7px` in the same yellow, and its author computed to exactly `18 × 0.9 = 16.2px` in the same yellow at `opacity: 0.82` (the preserved hierarchy) — then set a *book-level* override to Serif on top of that and confirmed, via a direct `GET /library`, that the book's own `_style.cardFontFamily` (`"serif"`) and the library-wide `style.cardFontFamily` (`"mono"`) were independently correct, and that the book's own card visually picked up the serif stack while the library-wide default stayed monospace elsewhere.

**`cardBold`/`cardItalic` and the three self-hosted fonts** were verified through the same real panel plus `getComputedStyle`: toggled Bold and Italic on and confirmed a preview title resolved to `fontWeight: "700"`/`fontStyle: "italic"`; specifically confirmed the `undefined`-not-`"normal"` mechanic by toggling Bold back off and reading both the status label (`font-medium`, resolved to `500` — its class's own weight, unclobbered) and the title (no class, resolved to plain `400`) in the same check; selected Playfair Display from the font dropdown and confirmed via `document.fonts` that it genuinely loaded (`status: "loaded"`) as a real `@font-face`, not just that the CSS declared it.

### Auto cover resolution — now a global, byte-caching backend service, not a client-side chain

The ENTIRE fallback chain — Kobo CDN, Open Library, Google Books, Hardcover — used to live here, in `lib/covers.ts`, re-run in full by every single browser tab that ever rendered a given book. Reported live in exactly those terms: *"we should create a sort of database for bookcovers, so when they load the first time we save them in a db, and when the user loads a second time instead we check our db if the bookcover already exists and avoid requesting cdn."* That chain now lives entirely server-side, behind a real cache — see `backend/src/modules/covers`' own README section for the cache/race/rate-limit details. This section covers what changed on this side.

**`lib/covers.ts` shrank to almost nothing**: `normalizeIsbn`, `normalizeImageId`, and `statusLabel` are the only exports left — everything else (`koboCoverUrl`, `openLibraryCoverUrl`, `coverCandidates`, `searchOpenLibraryCover`, `searchGoogleBooksCover(ByIsbn)`, `resolveFallbackCover`) was deleted outright, not deprecated. `scripts/test-covers.mts` shrank alongside it, from 5 sections/30 tests down to 2 sections/15 — the resolution logic it used to test now only exists behind a real network boundary this app's "runs standalone under plain tsx, no mocking" test convention was never meant to cover; that coverage now lives as live backend verification instead (see the backend README).

**`api/covers.ts`'s shape changed from a single Hardcover proxy call to the one general-purpose resolve call**: `resolveCover({isbn, imageId, title, author})` hits `GET /covers/resolve`, returning `{url: string | null}` regardless of whether that url came back from cache or a fresh resolve — the frontend never needs to know or care which.

**`CoverImage` (`BookCard.tsx`) rewritten around exactly one network call instead of a whole in-browser chain**: a book's own `_coverUrl` (a genuine custom gallery cover — unchanged, still always tried first with zero network cost) renders immediately if present; everything else makes exactly one `resolveCover()` call and renders whatever comes back, `null` included (the fallback icon, same as before). An `onError` on a `_coverUrl` image (a saved gallery cover whose file has since gone missing, or gone stale some other way) now falls through to a fresh `resolveCover()` attempt rather than just giving up — one additional case this rewrite happened to fix along the way, not something separately requested.

**`onCoverResolved` and its whole write-back path are gone** — `LibraryPage.tsx` used to debounce and flush every auto-resolved cover back into the book's own `_coverUrl` field, specifically so the NEXT load wouldn't have to re-resolve it. That entire mechanism (`pendingCoverUpdates`, `flushTimerRef`, `handleCoverResolved`, `flushCoverUpdates`) is exactly what the new backend cache replaces, and better — the old per-account write-back only sped up the SAME account's next load; the new cache is warm for every account, immediately, the first time ANY of them resolves a given book. Removing it also undoes a real conflation the old design carried: a `_coverUrl` set by auto-resolution and a `_coverUrl` set by a genuine custom gallery cover used to be indistinguishable in the saved data (see `lib/merge.ts`'s updated doc comment) — after this change, `_coverUrl` is only ever written by `lib/bookCovers.ts`'s `setBookCover`, i.e. only ever means "the user genuinely picked this."

**One thing deliberately preserved, checked against `LibraryStylePage.tsx` before touching it**: the "does this book have a `_coverUrl`" gate stayed a plain presence check, NOT gated on `_coverImageId` also being set (which would have more formally distinguished "real custom cover" from anything else). `LibraryStylePage.tsx`'s own `PREVIEW_BOOKS` set `_coverUrl` directly on fake preview objects with no `_coverImageId` at all — gating on both fields would have sent those preview cards through a real, pointless `resolveCover()` network call. Kept as a plain `_coverUrl` presence check, which also just so happens to preserve backward compatibility for any legacy `_coverUrl` already saved in real accounts from before this change.

Verified with the trimmed pure-logic suite (`normalizeIsbn`/`normalizeImageId`'s accept/reject shapes only, now that everything else moved server-side) and end-to-end in a real browser against the real backend: loaded the real 26-book test library cold and confirmed every cover rendered via `resolveCover()` calls, then reloaded and confirmed the identical covers rendered from cache — network panel showing `/covers/cached/:id/file` hits instead of external CDN calls, directly satisfying the original "avoid requesting cdn" ask; timed a genuine cache MISS against the identical book's own cache HIT afterward (~2.1s vs ~0.25s, an ~8x speedup) with the SAME served id confirming real caching, not just a faster re-resolve; confirmed a `_coverUrl`-bearing book renders with zero network calls at all; confirmed a custom cover assigned via the Gallery picker still always wins over the global cache, for that account, exactly as scoped ("its global until the user saves its own bookcover then that book should render the uploaded user bookcover"); confirmed `LibraryStylePage.tsx`'s preview cards still render with no network calls at all, catching what would have been a real regression before it shipped.

### Gallery and custom book covers

`/dashboard/gallery` — a per-account pool of uploaded images, backed by a real new backend module (`backend/src/modules/gallery`, see its own README section for the upload validation/re-encoding pipeline). Unlike everything else this frontend touches, this genuinely needed backend changes: uploading, storing, and serving image bytes isn't something the existing `library`/`auth` modules could just absorb as another opaque field.

**Assigning a cover**: every `BookCard` (everywhere one renders) has a small "Cover" button, stacked directly under "Style" (same top-left, hover-visible, accent-colored-once-set treatment) — opens `CoverPickerModal.tsx`: a grid of the account's gallery images to pick from, an inline drag-and-drop/file-picker to upload a new one on the spot (auto-assigned immediately on upload, no second click needed), and — once a book has a custom cover — a "Remove custom cover" link to go back to normal auto-detection. Deleting an image straight from the picker's grid works too, with the same "any book using it falls back automatically" behavior as deleting from the Gallery page itself (below).

**Reuses the existing cover-resolution chain instead of adding a new one**: `lib/bookCovers.ts`'s `setBookCover` just sets `book._coverUrl` — the exact same field `CoverImage` (`BookCard.tsx`) already tries first, ahead of the Kobo CDN/Open Library chain (see `lib/covers.ts`), and the same field a normal auto-resolved cover ends up persisted to via `LibraryPage.tsx`'s `flushCoverUpdates`. The only genuinely new field is `_coverImageId` — pure bookkeeping so a later gallery-image deletion knows which books' `_coverUrl` it's actually responsible for, versus a `_coverUrl` that came from ordinary auto-resolution and has nothing to do with the gallery. Same "opaque blob" reasoning as `lib/groups.ts`: no backend change to `library` needed for any of this, it's just more fields on a book object.

**Deleting a gallery image scrubs it out of every book that used it as a cover**, in the same save — `lib/bookCovers.ts`'s `scrubImageFromBooks`, the mirror image of `lib/groups.ts`'s book-delete-scrubs-groups logic (there: delete a book, scrub it from groups; here: delete an image, scrub it from books). Implemented once, in `hooks/useDeleteGalleryImage.ts`, and used identically from `GalleryPage.tsx`'s own delete button and from inside `CoverPickerModal.tsx` — a book that had the deleted image assigned just falls back to its normal auto-detected cover, no broken image, no crash. `GalleryPage.tsx` shows a "Cover for N books" count on each image (computed against the live library) precisely so deleting a still-in-use image is an informed choice, not a surprise — the delete confirmation itself repeats the count.

**Upload restrictions** (the actual validation lives server-side, see the backend README — this is what a user sees): JPEG/PNG/WebP/HEIC accepted by the file picker's `accept`, up to 20 MB, re-encoded server-side to a capped size with all metadata (including any GPS location data) stripped. A rejected upload (wrong file type, too big, over the account's storage quota) shows inline in whichever picker (Gallery page or the modal) it was attempted from.

**A gallery image can be deleted from every place it's shown, not only the Gallery page** — three pickers show gallery images (`GalleryPage.tsx` itself, `CoverPickerModal.tsx`'s cover picker, `components/murals/pickers.tsx`'s `GalleryImageGrid` for a mural's Image block), and until now only the first two could delete one; `GalleryImageGrid` offered no way to prune the pool at all, forcing a detour to the Gallery page for something as simple as "that upload was a mistake" while already looking right at it inside the block editor. Brought up to parity with the other two: same hover-reveal `×` button per tile, same real confirm dialog, same `useDeleteGalleryImage()` (the scrub-aware hook — not the plain `useGalleryImages().remove()` — so a book/mural cover or another block referencing the deleted image gets cleaned up too, not just this one block's own reference). `GalleryImageGrid`'s tile markup changed from a single `<button>` to a `<div role="button">` hosting the delete button as a real nested child, the same restructure `CoverPickerModal.tsx`'s own grid already needed for the same reason (a `<button>` can't validly contain another interactive element).

**Deleting the image a block currently has selected clears that block's own local draft, not just the saved data** — `BlockConfigPanel.tsx` edits a draft-then-Save, so the scrub `useDeleteGalleryImage()` runs against the *saved* library document doesn't reach the in-memory draft sitting open in the panel. `GalleryImageGrid`'s new `onImageDeleted` callback lets the caller check "was the image I just deleted the one THIS block currently has selected?" and clear its own `imageId` if so — otherwise clicking Save afterward would re-persist a now-dangling reference, undoing the scrub that just ran server-side.

Verified with new pure-logic test coverage (`scripts/test-book-covers.mts` — `setBookCover`/`clearBookCover`/`scrubImageFromBooks`, including the no-op-returns-the-same-array-reference convention shared with `removeBooksFromAllGroups`) and end-to-end in a real browser against the real backend pipeline (not mocked): uploaded a real PNG, confirmed it came back re-encoded to WebP at a smaller byte size; confirmed a non-image upload is rejected with `422`; assigned it as a book's cover from both the Library page and a Series section and confirmed `_coverImageId`/`_coverUrl` persisted correctly via a direct `GET /library` in both cases; confirmed the `BookCard`'s `<img>` actually loads the gallery URL (`naturalWidth` checked, not just that a request fired); confirmed "Remove custom cover" clears the override while leaving the gallery image itself untouched; confirmed deleting the gallery image (from the Gallery page) scrubbed `_coverImageId`/`_coverUrl` off the book that was using it, reverting it to normal auto-detection with no crash; confirmed the served file's `Cache-Control` and content-type headers, and that a deleted image's URL correctly 404s afterward. Separately verified the new Image-block deletion path end-to-end: uploaded an image, added an Image block referencing it, opened the block's config panel and confirmed a real hover-reveal delete button now exists there (it didn't before); selected the image, deleted it from inside the panel, confirmed the real confirm dialog fired with the expected wording, confirmed on confirming the panel's own grid updated to "No images in your gallery yet" without needing to close and reopen anything; confirmed on the actual Gallery page afterward that the image was genuinely gone server-side, not just hidden locally.

### Murals — configurable freeform dashboards

`/dashboard/murals` — a mural is a named, freeform dashboard you build yourself out of "blocks": a book spotlight, a hand-picked "Top 5 Books This Year" shelf, a featured quote, a photo, a stats strip. You can have several (`MuralsListPage.tsx`, same rename/delete list pattern as Series/Collections — see below for how creating one differs), and each gets its own canvas at `MuralEditorPage.tsx` (`/dashboard/murals/:muralId`).

**Freeform, but snap-to-grid, not pixel-free**: true arbitrary-pixel positioning would mean hand-rolling collision detection and resize handles from scratch. `MuralCanvas.tsx` wraps `react-grid-layout` (pinned to `1.5.4` — its `2.x` is a from-scratch rewrite with a genuinely different API, incompatible with the `@types/react-grid-layout` package and the classic `WidthProvider`/`draggableCancel` shape this is built against) with `compactType={null}` and `preventCollision` — blocks can be dragged/resized to any grid cell, stay exactly where you put them (RGL's default auto-compacts everything upward, which would fight a "arrange it your own way" wall), and never silently overlap. Persists on drag/resize **end** only (`onDragStop`/`onResizeStop`, not the continuously-firing `onLayoutChange`) — the `layout` prop is otherwise sourced straight from the saved document, so echoing every intermediate drag frame back through a save round trip would mean dozens of redundant `PUT`s per gesture.

**A removed block's gap closes automatically — but only right then, never as a standing behavior.** `compactType={null}` above is deliberate: while you're actively arranging a mural, nothing should auto-rearrange out from under you. But when a block actually *disappears* — a direct delete, or scrubbed away because the book/image it referenced was deleted elsewhere in the app — leaving a permanent dead zone where it used to sit is a real, reported problem (a mural with an Image block whose gallery image got deleted left a tall empty gap at the top of the canvas, with everything below it stranded exactly where it had been). `lib/murals.ts`'s `compactBlocksVertically` reimplements the same "gravity pack" algorithm react-grid-layout's own `compactType: "vertical"` uses (sort by y-then-x, slide each block up as far as it can go without colliding with an already-placed one — only `y` ever moves, a block never changes columns) as plain data-in/data-out logic, called as a one-time pass from exactly three places: `removeBlock`, and both `scrubBooksFromMurals`/`scrubImageFromMurals` — but *only* when a whole block actually vanished, never when a shelf/quote-collection merely lost one member and stayed put (nothing disappeared from the canvas in that case, so nothing needs to shift). Guarded the same way the scrub functions' own no-op convention already works: a `removeBlock` call for a block id that doesn't exist, or a scrub that didn't touch anything, returns the exact same array reference rather than forcing a pointless rearrangement.

Verified with new pure-logic test coverage (`scripts/test-murals.mts` gained four sections: `compactBlocksVertically` directly — a gap between two stacked blocks closes, two blocks genuinely side-by-side at the same height both stay put (no false cross-column collision), a block slides all the way up past a now-empty middle rather than stopping short; `removeBlock` closing the gap it leaves, and being a true no-op — same array reference — for a nonexistent block id; `scrubBooksFromMurals` closing the gap a fully-removed spotlight leaves for a shelf sitting below it, while confirming a shelf that merely lost one member keeps its *exact* original layout untouched; `scrubImageFromMurals` closing the gap a removed image block leaves for whatever sits below it) and end-to-end in a real browser: built a real mural with an Image block on top and a Text block below it, confirmed via each block's actual `react-grid-layout` DOM transform that the Text block sat at `translate(10px, 124px)`; deleted the Image block's underlying gallery image from the Gallery page (the exact real-world path that produced the reported empty gap); confirmed the Image block was gone and the Text block's transform had moved to `translate(10px, 10px)` — the gap closed for real, not just in the saved data.

**Edit mode / View mode**, same toggle pattern as the book-delete select-mode: View is the clean read-only render; Edit reveals drag handles, resize corners, an "Add block" menu, and each block's own ⚙ settings button. Mural editing is desktop-only for now — on touch devices the editor renders the mural read-only with an "edit on desktop" hint (decision D-D in the UX roadmap).

**One settings icon per block, not three** — used to be three always-hoverable icons (🎨 Style / ⚙ Configure / × Delete) sitting directly on the block; now a single ⚙ opens a small dropdown with Style/Configure/Duplicate/Delete, the same "one compact control surfaces this item's actions" shape `BookCard`'s Style/Cover buttons and `GroupsPage.tsx`'s per-series Delete/"Manage books" controls already keep to, just one step more consolidated since a block carries more actions than either of those. Delete still has no confirmation dialog (composing a mural means adding/removing blocks constantly, and re-adding one is cheap, unlike deleting a book/image/mural itself) — only the *menu* changed, not that behavior. `MuralsListPage.tsx`'s own mural cards got the identical treatment for the same reason: what used to be separate "Rename"/"Delete" text buttons on each card is now one ⚙ opening a dropdown with both — same component, same behavior, a different context (a plain card background instead of arbitrary block content/imagery, so its trigger uses a subtler ghost-icon style rather than the block's dark translucent circle).

**Duplicate** — `lib/murals.ts`'s `duplicateBlock` copies a block's type/content/style with a fresh id, landing below everything already on the canvas at the ORIGINAL block's own current size, not the type's default footprint (a spotlight you resized to `w:6,h:5` duplicates at `w:6,h:5`, not back to its type's starting `w:3,h:4`). No config panel opens afterward, unlike adding a fresh block — the whole point of duplicating is that it's already fully set up; drag it wherever or tweak it from there. Same no-op convention as `removeBlock`/the scrub helpers: a nonexistent block or mural id returns the exact same array reference rather than a pointless no-op save.

Verified with new pure-logic test coverage (`scripts/test-murals.mts` — the original is completely untouched after duplicating; the duplicate gets a genuinely new id; type/content/style are copied exactly; the duplicate's size matches the original's actual resized footprint rather than the type's default; the duplicate lands below every existing block without overlapping anything; both no-op cases — a nonexistent block id, a nonexistent mural id — return the exact same array reference) and end-to-end in a real browser: created a Text block with real content, saved it, opened its ⚙ menu and confirmed "Duplicate" now appears between Configure and Delete; clicked it and confirmed — via each block's actual `react-grid-layout` DOM transform — a second block appeared with identical text content, positioned cleanly below the original with no overlap, and confirmed no config panel opened in the process.

**Tier list — the tiers are the configurable thing, not just their contents.** Every other "pick some books" block type (Shelf, Quote collection) has a fixed shape: a title plus an ordered pool. A tier list needed a second axis — the RUNGS themselves are user data, not a fixed S/A/B/C/D scale with books slotted into it. `TierDefinition` (`lib/murals.ts`) is `{ id, label, color, bookKeys }` — a tier is its own row with its own label, its own accent color, and its own ordered members — and the block itself is just `{ title, tiers: TierDefinition[] }`. A fresh block starts with five tiers (`defaultTiers()`, the familiar S/A/B/C/D, each a distinct mid-saturation preset color — deliberately not pale/pastel, since every tier's label renders as white bold text with no auto-contrast calculation, the same "the user's own color choice, no contrast solver" approach this app's other style panels already take for arbitrary background/text color pairs) but every one of the five is free to be relabeled, recolored, reordered, or deleted, and more can be added — `createTier(label, color)` is the one place a tier's id is ever minted, shared by both `defaultTiers()` and `BlockConfigPanel.tsx`'s own "+ Add tier" button so id generation for a tier never happens in two places.

**One rung, one book — `BlockConfigPanel.tsx`'s per-tier picker excludes books already sitting on any OTHER tier of the same block** (computed fresh on every render as `tiers.flatMap(t => t.bookKeys)`, not cached), so a book can't accidentally end up double-ranked. Each tier row gets its own color swatch (`<input type="color">`, the same pattern `StyleControls.tsx`'s border-color pickers already use), a label text input, ▲▼ reorder buttons, a Delete, its current members as removable chips, and its own "+ Add a book" toggle opening a `BookSearchList` scoped to books not yet placed anywhere on this block — five independent micro-pickers rather than one shared one, since which tier you're adding TO is exactly the thing that differs per-row.

**Deleting a tier drops its books with it** — no "where do these go" prompt, the same low-friction "removing a block/member while actively composing is cheap to undo" stance this whole panel already takes (Draft-then-Save at the top of this file's Murals section, and block removal itself having no confirm dialog). `scrubBooksFromMurals` (the same function every other block type's book-deletion cleanup goes through) gained a `tierlist` case: a deleted book's key is filtered out of whichever tier actually held it, and the WHOLE block is only removed once every tier ends up empty — a tier list with even one book left on one rung is still a real tier list, unlike a Shelf/Quote-collection which has exactly one pool of members to lose entirely. `compactBlocksVertically` only runs when the whole block vanishes (every tier empty), matching every other scrub case's "gap only closes when a block actually disappeared from the canvas, never for a mere member trim" rule.

**View mode** (`TierListBlockView`, `components/murals/blocks/BookBlocks.tsx`) stacks every configured tier as its own row — a fixed-width colored label on the left, its books on the right — but each row now sizes to its OWN content rather than an evenly-split `flex-1` slot (an earlier version of this view did that, and it was wrong: at a fixed row height, a rung with more books than fit on one line just silently scrolled its overflow behind a horizontal scrollbar, same as Shelf). A tier list is a "see everything on this rung at a glance" board, not a curated scroll-through sequence the way a Shelf is — so `TierRow` wraps a rung's covers onto additional lines (`flex-wrap`, fixed-height `h-24` tiles so the row's own height can be DERIVED from however many lines it wraps onto rather than needing one from a parent that doesn't have it yet) and grows taller instead, with `items-stretch` keeping the color label full-height alongside it regardless of how many lines that turns out to be. Every tier renders even when empty ("No books on this tier.") — a tier list's whole point is showing every rung you've configured, not hiding the ones nobody's filled in yet.

**Some books rendered wider than others in a tier row** — reported live: two covers sitting side by side at visibly different widths. Root cause is a classic flexbox trap, not a sizing typo: each cover tile is a flex item sized via `aspect-[2/3]`/a fixed height, but `MiniBookTile`'s title/author lines use `truncate` (`white-space: nowrap`), and per the flexbox spec, a flex item's *automatic minimum size* is its content's min-content width — UNLESS that item's own `overflow` is something other than `visible`. Same latent bug existed in `ShelfBlockView`/`CurrentlyReadingBlockView`'s tiles too (`aspect-[2/3] h-full`) — just never visibly reported there, since a horizontally-scrolling row has no neighboring line for a too-wide tile to visibly misalign against, unlike `flex-wrap`. ### App-styled delete confirmations

Every destructive action (deleting a book, series/collection, gallery image, or mural) used to confirm through the browser's native `window.confirm()` — functional, but visibly out of place: a plain OS dialog stamped with the page's own URL in its title bar, no way to style it, sitting on top of an otherwise fully custom UI. Replaced with `ConfirmDialog.tsx`'s `ConfirmProvider`/`useConfirm()` — same shape as `AuthContext.tsx`'s provider-plus-hook pattern, mounted once in `main.tsx` above `<App>` so any component can call it. `useConfirm()` returns a `confirm({ title, body?, confirmLabel?, danger? }) => Promise<boolean>` — the same "returns whether the user confirmed" contract `window.confirm` had, just async (a real modal can't block the way the native dialog did), so every call site became `if (!(await confirm({...}))) return;` in place of `if (!window.confirm(...)) return;`. Every existing call site was already inside an `async function`, so no caller needed restructuring beyond that.

Same modal shell the rest of the app already uses (`CoverPickerModal.tsx`'s `fixed inset-0 z-50 ... bg-black/40` overlay, `rounded-xl border ... bg-(--color-surface) shadow-lg` panel) — title + optional detail line, Cancel + a confirm button defaulting to `--color-danger` red (every call site today is a delete) with an optional `danger: false`/custom `confirmLabel` escape hatch for a future non-destructive confirmation. Backdrop click and Escape both cancel, same as the modals it sits alongside. **Cancel, not Confirm, gets focus when the dialog opens** — a deliberate safety default: every use of this is a destructive action, so a stray Enter press (the same key that drives a native `confirm()`'s default button) lands on the safe outcome instead of the destructive one.

Replaced seven call sites: `MuralsListPage.tsx`/`GroupsPage.tsx` (delete a mural/series/collection), `LibraryPage.tsx`/`GroupsPage.tsx` (delete N selected books), `GalleryPage.tsx`/`CoverPickerModal.tsx` (delete a gallery image, from the Gallery page and from the cover-picker modal respectively). Verified end-to-end in a real browser (not just typecheck): triggered the dialog from both a top-level page (Collections' own delete) and from a modal nested inside another page's tree (`CoverPickerModal`), confirming both a plain page-level trigger and a modal-inside-modal trigger render the dialog correctly on top; confirmed the rendered title/body text matches each call site's intent (via direct DOM inspection, not just visual review); confirmed `Cancel` is genuinely the focused element (`document.activeElement`) the moment the dialog opens; confirmed a dispatched `Escape` keydown closes the dialog and leaves the target undeleted; confirmed clicking the delete button actually resolves the pending promise and completes the real delete (the item was gone from the page afterward, not just the dialog closing).

## Theming the browser's own defaults (scrollbars, focus ring, text selection, `<select>` dropdowns, checkboxes/range sliders)

Six UI signals the browser/OS renders itself, not this app — a scrollbar, the ring around whatever's focused, the highlight behind selected text, the popup list a `<select>` opens, a checkbox's fill, a range slider's track/thumb — all used to show up in the browser's own stock colors (a white/gray scrollbar, a blue-ish focus ring, blue selection, a stark white dropdown list, blue checkboxes and sliders) with zero relation to the app's actual palette, most jarring on the dark theme. `index.css` now styles all of them, each the same way: real CSS rules reading the theme's existing `--color-*` custom properties rather than hardcoded colors, so light mode, dark mode, and the light↔dark toggle all carry every one of them along automatically — no separate light/dark rule to keep in sync when the theme itself changes.

**Scrollbars** — every scrollable area (the page itself, a modal's `overflow-y-auto` list, a mural Shelf block's horizontal book row) via two mechanisms, both needed: the standard `scrollbar-color`/`scrollbar-width` properties (Firefox, and newer Chromium) plus the `::-webkit-scrollbar-*` pseudo-elements (what Chrome/Safari/Edge actually render in practice today) — `--color-border` (resting thumb) / `--color-text-dim` (hover). Verified via `getComputedStyle`: `scrollbar-color` resolved to exactly `rgb(56, 52, 47)` (`#38342f`, dark mode's `--color-border`) over a transparent track, not a browser default; confirmed all four `::-webkit-scrollbar-*` rules actually compiled into the loaded stylesheet (`document.styleSheets`).

**Focus ring** — `*:focus-visible { outline: 2px solid var(--color-accent); outline-offset: 2px; }`, a universal selector (same convention the scrollbar rule already uses) so every focusable element in the app — inputs, selects, buttons, links, and this app's own `role="button"` cards/tiles with a real `tabIndex` (the mural list's own cards, the Gallery's image tiles) — gets it for free, no per-component styling to add or keep in sync. Deliberately `:focus-visible`, not plain `:focus`: a mouse click landing on a button shouldn't flash a ring, only real keyboard navigation (Tab) should. Verified live with an actual Tab keypress (not a scripted `.focus()` call — Chrome's `:focus-visible` heuristic often doesn't activate for JS-triggered focus, so that would have proven nothing): confirmed `element.matches(':focus-visible')` is `true` after tabbing to a control, and its computed `outline-color` resolved to exactly `rgb(224, 138, 82)` (`#e08a52`, dark mode's `--color-accent`) — a solid 2px ring, not the browser's own default.

**Text selection** — `::selection { background: var(--color-accent-soft); color: var(--color-text); }`, the same soft-accent-background pairing already used for badges elsewhere in the app (a series/book's "custom style" tag), so selected text reads as highlighted-but-still-normal-text rather than the browser's default blue block. Confirmed the rule compiled into the loaded stylesheet with both values correctly referencing the theme's CSS variables (`::selection`'s applied styles aren't independently queryable via `getComputedStyle` on a real element, so the stylesheet-rule check — the same technique used to verify the scrollbar's `::-webkit-scrollbar-*` rules — is the direct way to confirm what's actually shipped, rather than only trusting a visual read).

**`<select>` dropdown lists** — a closed `<select>` already picks up the theme through each usage's own `bg-(--color-surface)`/`text-(--color-text)` Tailwind classes, but the *open popup* listing its options is separately-rendered, OS-native UI that ignores those classes and falls back to a stark white list regardless. `select, option { background-color: var(--color-surface); color: var(--color-text); }` is the one part of that native popup real CSS can actually reach in every major browser, applied once globally rather than duplicated at each of the app's `<select>` usages (`MuralsListPage.tsx`'s sort control, `StyleControls.tsx`'s several dropdowns). Not a full custom dropdown, and said so rather than implied otherwise: the highlight color for the currently-hovered/keyboard-selected row inside the open list is drawn by the OS/browser itself and stays whatever default the platform uses — no cross-browser CSS property reaches it, so this is a background+text theme for the popup, not pixel-perfect control over every part of it. Verified via `getComputedStyle` on both a `<select>` and one of its `<option>` children: both resolved to exactly `rgb(36, 34, 32)` background (`#242220`, dark mode's `--color-surface`) and `rgb(236, 232, 227)` text (`#ece8e3`, dark mode's `--color-text`) — real theme colors, not the browser's own white-list default; confirmed the `select, option` rule itself compiled into the loaded stylesheet.

**Checkboxes and range sliders** — every style panel in the app (Library style's Card layout/appearance/border sliders, a series/book's own override panel, a mural block's `BlockStylePanel.tsx`) is built almost entirely out of these two controls, and both used to render in the browser's stock blue with no relation to the theme. Two different treatments, matched to how much each control actually needed: `:root { accent-color: var(--color-accent); }` alone is enough for checkboxes — native checkbox rendering is already about as minimal as it gets, it only needed the right color, not a rebuild. Range sliders got a fuller pass: the native thumb+track combo (a thick track, a large beveled thumb) reads noticeably heavier than the rest of the app's thin-bordered, flat aesthetic, so it's `appearance: none` and hand-drawn from there — a slim 4px track in `--color-border`, a small flat 14px circular thumb in `--color-accent` with no border or shadow — a genuine redesign toward "minimalist," not just the existing OS shape recolored. Needs both `::-webkit-slider-thumb`/`::-webkit-slider-runnable-track` (Chrome/Safari/Edge) and `::-moz-range-thumb`/`::-moz-range-track` (Firefox) — there's no engine-agnostic way to restyle a native range control. The blanket `*:focus-visible` rule above is overridden specifically for range inputs (`outline: none` on the base element, a real 2px ring on the thumb pseudo-element instead) — with a 4px-tall track, a rectangular outline around the whole element read as a stray thin bar rather than a focus ring; the ring belongs on the thumb, where the user's actual attention is. Verified via `getComputedStyle`: a range input's track resolved to exactly `4px` tall in `rgb(56, 52, 47)` (`#38342f`, dark mode's `--color-border`), and its `accent-color` (plus a checkbox's) resolved to exactly `rgb(224, 138, 82)` (`#e08a52`, dark mode's `--color-accent`); confirmed the `::-webkit-slider-thumb` rule itself compiled into the loaded stylesheet at exactly `14px`/`border-radius: 50%`/`background: var(--color-accent)` (pseudo-element styles for range parts aren't reliably queryable via `getComputedStyle` on the real element — Chrome's own resolution for that specific query returned the track's values instead of the thumb's when tried directly, so the stylesheet-rule check, the same technique already used for `::-webkit-scrollbar-*`, is the trustworthy way to confirm what's actually shipped here); confirmed a focused range input's own `outline-style` is `none` (the override took), consistent with the ring living on the thumb instead.

## SQLite import: npm package instead of the viewer's base64-inlined vendor bundle

The viewer had to inline sql.js's WASM binary as base64 text inside its single HTML file, specifically to dodge Chrome blocking `fetch()` of local files when that page is opened via a plain `file://` double-click. That constraint doesn't apply here — this is a real bundled app served over http (dev server or a built static host), never `file://` — so the plain `sql.js` npm package + Vite's asset pipeline (`import sqlWasmUrl from "sql.js/dist/sql-wasm.wasm?url"`) is the more idiomatic fit: no giant inlined string, Vite serves the `.wasm` file as a normal asset with the right MIME type.

## Text-link hover treatment: no underlines

Every text link/button in the app (rename-by-clicking-a-title, "Style"/"Manage books"/"Delete" on a series or collection, "Remove custom cover," "Back to Murals," "Change" on Settings' username, etc.) used to add `hover:underline` on top of whatever color it already had — a dated, slightly heavier-handed hover cue than the rest of the app's minimal aesthetic. Replaced everywhere with one of two patterns, chosen by what the link already was, never introducing underline again:

- **Colored links** (already `--color-accent` or `--color-danger`) — `transition-opacity hover:opacity-80`. A same-color fade reads as "interactive" without needing a second color.
- **Neutral/bold text acting as a link** (a clickable title like the library name or a series/mural card's name, or a `--color-text-dim` action word like "Style"/"Manage books") — `transition-colors` plus a hover destination color: `hover:text-(--color-accent)` for titles (the same accent a real link would use, signaling "this heading is clickable"), `hover:text-(--color-text)` for dim secondary actions (brightening to full-strength text, the same "dim → text" cue GroupsPage's own controls already used everywhere except its own "Style"/"Manage books" links, which had `hover:underline` layered on top of that same `hover:text-(--color-text)` redundantly).

11 call sites changed: `SettingsPage.tsx` ("Change"), `CoverPickerModal.tsx` ("Remove custom cover"), `LibraryPage.tsx` (library name), `GroupsPage.tsx` (series/collection name, "Style", "Manage books", "Delete" — four in one file), `MuralsListPage.tsx` (mural name), `MuralEditorPage.tsx` ("Back to Murals"), `BlockConfigPanel.tsx` (two "Remove" links, Shelf's book list and Quote collection's quote list). Verified via `getComputedStyle` under a real (CDP-driven) `:hover`, not just a className diff: confirmed `text-decoration-line` is `none` at rest and while hovered on every changed site, and confirmed the intended property actually moves on hover — `opacity` dropping to `0.8` on a colored link, `color` shifting to the accent's `rgb(224, 138, 82)` on a clickable title.

## How auth actually works here

- `src/auth/tokenStore.ts` — the session (`user`, `accessToken`, `refreshToken`) lives in a plain module-level variable + `localStorage`, *not* React state. `src/api/client.ts` (a plain module, no hooks available) needs to read the current token and write a refreshed one back; `src/auth/AuthContext.tsx` wraps the same store with `useSyncExternalStore` purely so components re-render when it changes. One source of truth, two ways of reading it.
- `src/api/client.ts`'s `apiFetch` is what every authenticated call goes through: attaches the current access token, and on a `401` tries exactly one refresh-and-retry (via `POST /auth/refresh`) before giving up — concurrent 401s share a single in-flight refresh rather than each firing their own. If the refresh itself fails, the session is cleared, and the next render of `RequireAuth` redirects to `/login`.
- `src/auth/RequireAuth.tsx` (must have a session) and `src/auth/RequireUsername.tsx` (must also have a username) are both route-level guards, nested in `App.tsx` rather than checked per-page — `RequireUsername` only ever needs to exist because Google sign-ins can land mid-setup (a session with `user.username === null`).

## Not built (flagged, not silently skipped)

- No password-reset/email-verification UI (the backend doesn't have those endpoints yet either — see backend README).
- No book detail view / highlights view yet — cards render, but clicking one doesn't do anything (`onClick={() => {}}` in `LibraryPage.tsx` / `GroupsPage.tsx`). The old viewer's highlight modal was never ported.
- No search/filter/sort on the library grid — the old viewer had these; this is a fresh build that only has the minimum for "see your saved library." (Series and Collections give one form of organization now — see above.)
- No quick "add to collection" from a book card itself — adding a book to a collection is only done from the Collections page's "Manage books" picker, not inline on the Library grid.
- PWA icon is a single flat SVG at all sizes — fine for modern browsers, but no maskable-safe-zone PNG variants for platforms that want one.
- No test suite — verified manually end-to-end (signup → import → logout → login-again-and-see-persisted-data) while building this, not via an automated test runner.
- No select-mode bulk delete on the Gallery page — images are deleted one at a time (with a confirmation each time), unlike the Library/Series/Collections pages' select-mode bulk delete for books. Fine at gallery-pool scale; would follow the same pattern if it became worth it.
- No image-editing (crop/reorder/rename) in the gallery — upload, assign as a cover, delete. Re-uploading is the only way to change one.
- Murals list cards show only a block count, not a live thumbnail/preview of the actual wall — you have to open one to see it.
- No "duplicate mural" — building a similar one means starting from scratch.
- The Gallery page's "Cover for N books" usage count (shown before deleting an image) only checks book covers, not mural Image blocks — deleting a gallery image still correctly removes any mural block using it (`scrubImageFromMurals` always runs), it just isn't reflected in that specific pre-delete warning number.
- No responsive breakpoint story for the mural canvas — one fixed 12-column grid regardless of viewport width; a wall arranged on desktop can look cramped on a narrow window. `react-grid-layout`'s `Responsive` variant would be the natural fix if this became worth it.
- Socials is connect/disconnect only — scoped that way deliberately (see "Socials" above), not a partial build of something bigger. Nothing in this app posts to, or reads from, a connected platform yet.
- X/Instagram/Threads/TikTok's connect buttons haven't been exercised against a real developer app (no credentials exist for any of the three yet) — what's verified is everything that doesn't need them: correct disabled state with no crash, and (via Bluesky's real, live-verified flow) the same storage/UI path all five platforms share. See `backend/README.md`'s own "Not built" for the same caveat from that side.
- No "last used" or "needs reauthorization" state on a connected platform — a token can silently expire or be revoked on the platform's own end, and Settings would keep showing it as connected until the next action against it actually fails (and nothing calls out to a platform yet to trigger that).
- Reordering within a Shelf/Quote-collection is ▲▼ buttons, not drag — a second drag surface nested inside blocks the canvas itself drags would fight for the same gesture.
